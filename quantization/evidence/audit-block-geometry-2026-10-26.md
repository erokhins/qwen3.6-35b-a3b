## The hand-typed row that was wrong

| type | was | derived from the header | delta |
|---|---:|---:|---:|
| Q5_K | 5.5625 | 5.5 | +0.0625 |

`MXFP4` derives from member sizes only (17 B per 32 elements = 4.25 bpw): this header carries no `static_assert` for it, so that row is a single reading, unlike every K-quant row above it. It is a policy-row width, so it is worth knowing which rows are doubled and which are not.

What the wrong row was worth on the audited file, computed from the file's own tensor records and not from the bpw delta alone: **74.00 MiB** over its 37 Q5_K tensors — arithmetic in quantization/evidence/audit-published-quant-2026-10-26.md, section "A hand-typed width: the 74 MiB, and where my 232 MiB went". It touched only the published-file width map. No `quant_scenarios.py` policy row uses Q5_K, so policy A's 19.59 GiB resident and 2.331 GiB/token do not move.

Element-count-per-block is a claim about the type, not a reading of a struct, and it is witnessed by data instead: `check_file()` fails unless `sum(row_bytes) + data_start` reproduces a real file's size exactly. On the audited file it does: 22,123,538,944 + 10,990,048 = 22,134,528,992 bytes.
