# MXFP4 — what the format is, what it is for, and what it is worth on this box

Raised by D-08 (which 4-bit format the routed experts get). Read 2026-10-26.

**Sources, and what each is good for**

- **OCP Microscaling Formats (MX) Specification v1.0** (and v1.1), opencompute.org — the format
  definition: block + scale + narrow element type, and the E8M0 scale type.
- **Microscaling Data Formats for Deep Learning**, arXiv 2310.10537 — the paper behind the standard;
  states MXFP4 storage as **136 bits = 17 bytes per 32 elements** (→ 4.25 bpw).
- **AMD Instinct MI350 product page** and the **CDNA4 architecture whitepaper** — MXFP6/MXFP4 as
  *hardware matrix datatypes*.
- **Microbenchmarking NVIDIA's Blackwell Architecture**, arXiv 2512.02189 — native FP4/FP6 on Blackwell
  tensor cores; no pre-Blackwell NVIDIA part has FP4 tensor cores at all.
- **llama.cpp b11869 (commit `d327bf1`)**, files read: `ggml/src/ggml-common.h` (`block_mxfp4`,
  `block_nvfp4`, `block_q4_K`, `block_q8_0`, `block_q6_K`), `ggml/src/ggml-cuda/dequantize.cuh`
  (`dequantize_mxfp4`), `ggml/src/ggml-cuda/mmq-config-rdna3-5.cuh` (the MXFP4 MMQ cases),
  `ggml/src/ggml-hip/CMakeLists.txt` (the HIP backend compiles `../ggml-cuda/*.cu`).
- In-repo: `quantization/evidence/unsloth-qwen3.5-35b-a3b-2026-10.md` (the KLD numbers),
  `quantization/evidence/llama-cpp-tensor-policy-2026-10-26.md` (which tensors llama.cpp will and will
  not quantize).

## The format, precisely

MX = a narrow element type **+ one shared scale per block of 32 elements**. MXFP4's element type is
**E2M1** (sign + 2-bit exponent + 1-bit mantissa), so a weight can only take one of 8 magnitudes —
0, 0.5, 1, 1.5, 2, 3, 4, 6 — times the block scale. The scale is **E8M0**: an unsigned biased exponent,
i.e. **the scale can only be a power of two**. 17 bytes per 32 weights = **4.25 bpw**, and llama.cpp's
struct is exactly the spec, with a static assert to prove it:

```c
#define QK_MXFP4 32
typedef struct {
    uint8_t e;              // E8M0
    uint8_t qs[QK_MXFP4/2];
} block_mxfp4;   // == 1 + 16 bytes per 32 weights
```

The alternative D-08 weighs against it, **Q4_K**, is 4.5 bpw with far richer scale arithmetic: a
256-weight super-block of 8 sub-blocks of 32, each sub-block carrying **both a 6-bit scale and a 6-bit
min** (asymmetric), plus two fp16 super-block scales that scale those scales — `block_q4_K` is
`2 × half + 12 B scales + 128 B nibbles = 144 B / 256` ("Effectively 4.5 bits per weight", the
header's own comment). Same 32-element grid granularity, much finer scale grid: a Q4_K block can place
its grid anywhere, an MXFP4 block can only put it on a power-of-two line, so the best representable
scale is up to a factor √2 (≈41 %) away from the ideal one.

Adjacent and worth knowing: llama.cpp also has `block_nvfp4` — 64 weights, **four UE4M3 sub-scales, one
per 16 elements**, 36 B / 64 = 4.5 bpw. NVIDIA's answer to the same problem, with a finer block and a
non-power-of-two scale. It is not on our table (no FP4 hardware here either) but it is why "4-bit" is a
design space, not a single thing.

## What MXFP4's advantage actually is — and why this box cannot use it

The standard exists so that hardware can multiply blocks **natively**: because the scale is a power of
two, a block-scaled matrix multiply is an exponent shift rather than a multiply, and the element
products fit a narrow integer path. That hardware is **newer than this machine**: MI350/CDNA4 lists
MXFP6/MXFP4 as matrix datatypes, Blackwell has native FP4/FP6, and no pre-Blackwell NVIDIA part has FP4
tensor cores. Nothing published places an MX/FP4 matrix instruction in RDNA3 or RDNA3.5 (gfx1151) —
which is *reasoning from the ISA*, not a measurement here; the corroboration below is stronger than my
sentence about it.

**Corroboration read out of the reference implementation rather than asserted:** llama.cpp does accept
MXFP4 on RDNA3.5, but through
`CASE(GGML_TYPE_MXFP4, 128, 2, 64, 16, GGML_CUDA_MMQ_SRAM_LAYOUT_Q8_1, …)` in
`ggml/src/ggml-cuda/mmq-config-rdna3-5.cuh` — the MXFP4 nibbles are **converted into a Q8_1-shaped
shared-memory tile** and consumed by the integer MMQ path. The dequant itself is a nibble table lookup
times the power-of-two scale: `y[j] = d * kvalues_mxfp4[q] * 0.5f` with
`d = ggml_cuda_e8m0_to_fp32(x[ib].e)` (`dequantize.cuh`). And `ggml-hip/CMakeLists.txt` globs
`../ggml-cuda/*.cu`, so **that is the gfx1151 path**, not a CUDA-only curiosity. Conclusion: on this box
MXFP4 is a *storage* format only — its headline advantage is unavailable, and whichever engine runs
(llama.cpp's or ours) pays a dequant either way.

## What it is worth here (policy arithmetic)

`python3 tools/quant_scenarios.py --read 237 210 190`, policy C is the MXFP4 variant of the decided
policy A:

| policy | resident | GiB/token | ceiling @237 / 210 / 190 |
|---|---|---|---|
| **A — experts Q4_K (decided)** | 19.59 GiB | 2.331 | 95 / 84 / 76 tok/s |
| C — experts MXFP4, rest Q8_0 | 18.63 GiB | 2.301 | 96 / 85 / 77 tok/s |
| D — experts IQ4_XS, rest Q8_0 | 18.63 GiB | 2.301 | 96 / 85 / 77 tok/s |

So the whole MXFP4 prize is **0.96 GiB of residency and ~1.3 % of ceiling**. It is not a residency
escape: both A and C fit the ~32 GiB co-resident budget comfortably (`devices/measured-facts.md`,
D-11), so this is a small speed/size trade against measured quality, not a feasibility question.

## The measured quality side (same model family, public)

From `quantization/evidence/unsloth-qwen3.5-35b-a3b-2026-10.md`, Qwen3.5-35B-A3B:

| quant | size | KLD 99.9 % |
|---|---|---|
| Q4_K_M | 18.49 GB | **0.5478** |
| MXFP4_MOE | 18.17 GB | 0.7789 |

Q4_K is the better approximation **and** within 1.8 % of MXFP4's size — and unsloth's own guidance is
"better to use Q4_K than MXFP4 when choosing between them". (A perplexity-only crowd claim that MXFP4
wins exists; the KLD comparison is the one that measures distribution shift, which is what a decoder
model is judged on. Per `pitfalls/60`, prefer the instrument that measures the quantity in question.)

## Where MXFP4 could still win, and the cheap test that would decide it

One genuine point in its favour **on this box**, and it is the mirror of the fact above: because a block
shares one power-of-two scale and the grid is symmetric, a block's contribution to a dot product is
`2^k × (int4 · int8 dot)`, so a kernel can accumulate **in integers for a whole block** and apply one
scale per block — no per-element float multiply, no 6-bit scale unpacking, no min subtraction. Q4_K
cannot do that: its scales are not powers of two and each sub-block has an offset.

So if our 4-bit decode ever turns out to be **dequant/issue-bound rather than bandwidth-bound** (the
failure class `pitfalls/20` warns about), MXFP4 is a legitimate lever. The test that would establish it
is not a debate: write both dequant inner loops in `prototype/moe_gemv` and time them on the real expert
shape. And per `pitfalls/30`, if MXFP4 ever needs a numeric band, that band has to be bought with a
floor probe and a geometry-derived must-catch set against a bf16 oracle — a 1.3 % speed claim does not
license a wider band.

## Status

**D-08's recommendation stays Q4_K**: better published quality at effectively the same size, no native
MX hardware on this box (the reference implementation repacks MXFP4 to Q8_1 here), and MXFP4's real
local edge — a cheaper dequant — is unmeasured. It stays **open rather than closed**, because the thing
that should decide it is a `prototype/moe_gemv` timing of the two dequant paths, not another read of
forum posts. IQ4_XS (policy D) is the same size as MXFP4 with better quality-per-byte but codebook
dequant cost, so it is decided by the same measurement.
