# speccheck/evidence/gdn-bf16-arm-disposition-2026-10-26.txt — how the `scan_in_bf16` arm is
# disposed of, and the measurement that disposes of it.
#
# The arm used to be adjudicated for CONTAINMENT only: every stage it moved had to sit inside
# `AFFECTED["scan_in_bf16"]`, and at least one had to move. That is not enough to answer the
# question the lane owed, because the licence it is contained by is the arm's own contract — a
# wrong contract would have been witnessed as containment. The question is: the arm declares it
# touches the scan, and it moves SEVEN stages. Is the declaration wrong, or does a bf16 scan
# really propagate past its own boundary?
#
# Decided by measurement, on the pinned rows, both blocks, both dispatch shapes:
#   (1) the stages whose STORAGE WIDTH the arm changed are exactly the scan-local four —
#       `q_hat, k_hat, scan_out, state` — asserted equal to `SCAN_LOCAL_STAGES`;
#   (2) the stages whose BYTES moved while their dtype did not are exactly the downstream
#       closure — `core_attn, normed, y` — asserted equal to `downstream_closure(SCAN_LOCAL)`;
#   (3) the other 12 stages, every one of them upstream of the scan, are bit-identical; a
#       pre-scan move would be bf16 propagating BACKWARDS and is a separate failure;
#   (4) the attribution: feed the reference's OWN `core_attn` bytes through the oracle's
#       `gated_norm` + `out_proj` and they reproduce the reference's `normed` and `y` BIT FOR
#       BIT. The downstream therefore contributes nothing to the disagreement, which leaves the
#       scan's storage width as the only cause.
#
# Verdict: the bf16 path really does propagate, and the contract was not wrong so much as
# UNTYPED — it is now derived (`AFFECTED["scan_in_bf16"] == downstream_closure(SCAN_LOCAL)`,
# asserted at import, and the derived stage set is the same seven stages, so the injection
# matrix's `arm=stub must_catch_missed == derived` denominator is unchanged at 2084). The arm is
# kept, not deleted, not skipped, not narrowed.
#
# What stays NOT ESTABLISHED, with its measured reason: torch's CPU backend has no BFloat16
# kernel for `triangular_solve` — the live probe returns
# `NotImplementedError: "triangular_solve_cpu" not implemented for 'BFloat16'` — so the arm does
# the solve the way the reference does it, F32 then cast back to the scan's storage width
# (`specification/04-gdn-linear-attention.md §04.4`'s scan-dtype row and
# `specification/04b-gdn-chunked-form.md §04b.4`: `torch_chunk_gated_delta_rule` casts
# q/k/v/beta/decay to float32 at the scan entry and solves in float32). The numerics of a bf16
# SOLVE therefore remain this lane's to establish, and are carried in `NOT_ESTABLISHED` with the
# probe's own exception string, which `section_selftest` requires to match the live probe.
#
# command: /home/erokhins/erokhins_projects/qwen3.5-0.8b/.venv/bin/python speccheck/gdn_ref.py --selftest
#   (the bf16-arm table lives inside `--compare-hf`, which `--selftest` runs; rc=0, SELFTEST
#   PASS). CPU only; no clock read, so no ms / tok/s / GB/s figure appears in this file.
#
# ---- the table, extracted from the run ----
